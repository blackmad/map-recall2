`pilot-segments.json` defines each directed street segment and side (`+1` is left, `-1` right). Coordinates come from the installed routing extract. Samples occur every 25 metres. Acquisition uses the municipal thumbnail service only to select a camera: that endpoint ignored requested heading in this pilot. Actual images are local ray-sampled perspectives from cached immutable municipal equirectangular images, using the project's Amsterdam north-at-image-center camera convention. Narrow alleys use wider, upward views to retain upper facade evidence. Extraction is bounded to the ArchitecturalRecipe vocabulary and rejects invalid JSON, colours, ratios or enum values. Raw proposals and failures remain separate from the source coverage manifest and runtime catalog. The compiler deduplicates overlapping observations using one strongest vote per 5m frontage cell. Ratios and colours in reviewed recipes are approximate rendering choices, not sampled or surveyed measurements. Uncertain sides are withheld: the Marcantilaan north-facing crops contain trees and road rather than a usable near facade. Construction-year eligibility and a 28m historic-family height guard preserve modern exceptions and towers. A missing or incompatible profile falls back to existing rendering defaults.

For runtime palette realization, `compileStreetAppearanceAssignments(profiles, fronts)` accepts actual exposed street-side wall runs with surveyed building identity, year and height. Feed it the complete profile segment cohort or an adequate source halo, excluding courtyard holes, hidden walls and curated/source appearance. It merges duplicate and overlapping parts of the same building on the same street side, partitions recipe eligibility by source date and height, and apportions the joint palette with largest-remainder quotas. Width-aware ordering realizes those quotas along the genuine frontage order. This prevents a minority dark facade's palette slot falling in an empty gap or an incompatible modern building. `streetAppearanceFrontageRecords(profile, assignments)` persists a sparse `{buildingId, recipeIndex}` table into `profile.frontages`; default wall resolution uses that frozen full-cohort table so separate streamed chunks and rendering modes see the same allocation. Corner street sides retain independent tables. This is approximate street composition, not a photographed building match or a POI-specific override.

The baker uses the same production wall-run and street-ray visibility as the game, keeping a 25m neighboring-footprint halo. It embeds a compact `streetFrontPaths` graph from the installed municipal routing extract so appearance does not depend on the active travel mode. Only street segments intersecting the profile bounds and halo are retained; coordinates are explicitly converted from the routing extract's latitude/longitude order. Routing, model exclusions, geometry, construction facts and compiler inputs are fingerprinted for reproducibility.

Before publication, the read-only `audit-frontages.ts` replays real source geometry and checks baked cohort reproduction, the compact graph against the complete graph, source hashes, and separately generated subsets. It reports palette share by unique building, exposed run and facade width: one wide modern building can legitimately occupy much more visible frontage than one narrow historic house even when count quotas are correct. `survey-admission.ts` rejects stale sources, missing provenance, phantom non-street fronts and split-dependent palettes. Passing this gate admits the build to visual review; it does not establish city-wide coverage or visual fidelity. Scale coverage only after the reference/gameplay views and renderer performance also pass review.
