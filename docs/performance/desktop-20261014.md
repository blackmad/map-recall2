# Desktop ride performance, second pass (2026-10-14)

Follows `docs/performance/desktop-20261013.md` (same route, same profiler,
same four configurations). That pass fixed the label overlay and landmark
view bounds and listed the next candidates by measured ms; this one takes
them: the HUD street-name walk, landmark ray picks, landmark matrix updates
and the bike's second render. Nothing the game shows changes. The iPhone
profile is still **pending** (desktop is the priority).

Method as before: Anne Frank Huis -> Rijksmuseum, car, chase, seeded
`Math.random`, 12 s holding ArrowUp after the city settles (aerial: camera held
~300 m up, rider stopped); uncapped frames (`--disable-gpu-vsync
--disable-frame-rate-limit`); owner rows are exclusive main-thread ms per frame,
mean of two wrapped runs (individual runs in brackets); frame rows are one
unwrapped run. Before = the committed bundles at `4f9c353d`; after = the four
fixes, served with `BUNDLES_DIR` from a local build. Before/after runs
interleaved. Machine shared with other lanes (load average 12-18 on 14 cores),
so single runs swing by +-1 ms; MapLibre's own render (untouched) moved
1.0-2.3 ms between runs and is the noise floor to read the rest against.

## The four fixes (one commit each, before/after in the message)

1. **HUD street names: per-cell candidate list, no walk when nothing can
   draw** (`src/canalRecall/game/streetLabelCandidates.ts`, used by
   `presentationRuntime.ts`; `road-network.js` `drawLabels` takes it as an
   optional sixth argument). A label can only pass the game's knowledge test if
   its name is in `_mapLabelNames` or `_knownPlaces`; when both are empty (a
   guest) the walk is skipped, otherwise the anchors of those names within
   reach of the camera's 256-unit cell are cached in anchor order until the
   cell, reach bucket or name set changes, and `drawLabels` still applies all
   its own tests to them (unit test: equal to the full walk, in order, over
   400 random cameras). `track.drawLabels` 0.51 / 0.54 -> 0.01 / 0.01 ms per
   frame in chase. The earlier grid index lost to its ascending sort; this one
   sorts only when the name set changes.
2. **Landmark picks: bounding-box pre-test per model, per-mesh BVH built in
   idle time** (`src/canalRecall/landmarks/pickBvh.ts`,
   `signature-landmarks-source.js`). The cost was not misses but hits and
   near-misses on big models (Pulitzer 39k triangles, Westerkerk 21k: three's
   Raycaster tests every triangle once inside a mesh's box and builds a full
   record per crossing). `nearestVisibleHit` returns what
   `intersectObject(group, true).find(visible)` returned (unit test, 2,400
   rays over mirrored/grouped/draw-ranged/mixed-side/instanced/hidden meshes);
   a pick never builds a BVH, it queues the model for idle time (forced after
   250 ms for at most 3 ms). In-page bench, 360 picks on a 24x15 grid in the
   aerial hold: 0.17-0.21 -> 0.013-0.022 ms per pick, identical id and depth at
   every point. `landmarks.inspectAtScreen` 0.21 / 0.19 -> 0.01 / 0.01 ms per
   frame aerial, worst call 6-7 -> 1 ms.
3. **Landmarks: compose placed models' matrices once**
   (`src/canalRecall/landmarks/staticMatrices.ts`). `matrixAutoUpdate =
   false` on every placed model (and its legacy scene and lights) after
   placement and on a swapped-in level; legacy model scenes also stop the
   per-render `updateMatrixWorld` walk and are refreshed where their contents
   change (level swap, highlight passes). CPU profile, chase:
   `updateMatrixWorld` inclusive 129 / 112 -> 46 / 58 us per frame
   (the rest is the bike, roofs, facades and trees); aerial: matrix work
   ~200 us per frame -> under the 30 us listing floor. Within noise on the
   wrapped layer owner.
4. **Bike: the x-ray and the model in one render**
   (`player-vehicles-source.js`). Why twice: the layer rendered the scene once
   with the x-ray override material (yellow, `GreaterDepth`, no depth write) and
   once normally; each render is a full three.js pass, and the override was
   transparent and double-sided, so three also split it into back and front
   draws. Now each mesh has an x-ray twin (shared geometry and material, made
   opaque-list with `CustomBlending` set to three's straight-alpha
   NormalBlending factors) that sorts ahead of the opaque model by
   `renderOrder`: the same x-ray-then-model order in one render. Committed
   bundle vs this, six frozen frames with the bike pushed into the blocks
   ahead (x-ray showing through a building): 0 pixels differ by more than
   30/765, identical yellow counts. Bike layer 0.27 / 0.29 -> 0.07 / 0.08 ms
   per frame; draw calls 466 -> 448 median.

**Bundles the integrator must rebuild:** `game-presentation.bundle.js`
(`npm run build:canal-game-presentation`, fix 1), `signature-landmarks.bundle.js`
(`node scripts/build-3d-bundles.mjs --only=signature-landmarks`, fixes 2-3),
`player-vehicles.bundle.js` (`node scripts/build-3d-bundles.mjs
--only=player-vehicles`, fix 4). `road-network.js` is a plain script and
committed; with the old presentation bundle it behaves exactly as before.

## Next, measured but not fixed

- **MapLibre's own render** is now the largest owner everywhere (1.0-1.9 ms
  per frame), untouched by either pass; its symbol/fill work and the tile
  upload batches are the next desktop target.
- **Signature landmarks layer** (legacy) 0.30 ms chase / 0.73 ms aerial: one
  `renderer.render` per model (97 entries aerial), each re-running light
  setup and render lists. Drawing all landmarks in one scene (the shared
  frame already does) or batching per light rig would cut it.
- **Shared-frame overlay x-ray**: the shared frame still draws the bike twice
  (`sharedFrame.ts` override pass); the twin approach could apply there too.
- **City prism picks** (`threeBuildings.inspectAtScreen`) 0.07-0.10 ms per
  frame aerial, worst ~2 ms: the next pick cost after the landmarks.
- **Game update + camera** ~0.3-0.4 ms per frame: not profiled below the
  owner level yet.
- iPhone 13 (4x throttle) profile of the four configurations: pending.
