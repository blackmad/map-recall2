# House line: faster house building (plan, 2026-11-10, approved by the user)

## Context

The user: "I'd really expect that by this point in the project, we'd be able to look at a canal house, write a description, pull in some kit parts and have it done in a few minutes. It seems like they still take far longer than that." Diagnosis agreed in chat (2026-11-10):

1. **No single spec.** Facts live in eight places (BAG/3DBAG, roof-facts, monument register, measured tints/glazing, shopfronts, kit locations, block-face libraries, hand measurements) and 29 source files read facade fields across at least five render paths. Each path reads its own subset: the Nieuwmarkt 4–22 row renders as flat-topped boxes while the register and `monument-gables.json` both know every gable (user photo vs game, 2026-11-09).
2. **No fast preview.** Seeing a house = world recompile + bundle rebuild + dev server + Playwright under `/tmp/canal-pw.sh`. Minutes per look, ten looks per lane.
3. **Publishing is heavy.** Every install triggers cell compile, shell re-bake, covers, goldens and the full gate; data changes pay a code change's price.
4. **Measurement is manual.** The panorama → rectified strip pipeline exists but was run block by block: ~226 strips vs 192,567 pands. Jev spike (#326): bays ±1 100 %, shopfront 85 %, gable confident-only 42 % coverage, finish 85 %; the bottleneck is crops, not the judge.
5. **Every house lane is a kit lane.** Missing components stall assembly; `docs/handoffs/kit-gaps.md` is prose and goes stale.

Outcome wanted: describe → render → compare → stage → publish in minutes per house, with Jev + register + panorama measurement filling the describe step for thousands of houses, and kit work driven by a derived queue.

Implementation runs through the Opus integrator session (`integrator-lanes-85`), which spawns lanes; this session writes the briefs and judges hand-backs (standing rule). Model per lane as marked.

## Design: the house line

One pipeline, five stations, each a command that runs alone in Node and is documented where the next session will look.

```
describe ──► preview ──► compare ──► stage ──► publish
(spec)       (PNG, 3 s)  (likeness)  (staging) (nightly batch)
```

### 0. Fix first (small, H1 step 0)
`scripts/world/pipeline.ts` `GLOBAL_INPUTS` does not list `monument-facts.json` and `CODE` does not list `facade/registerRecipe.ts`/`registerFacts.ts`, so `world:compile --changed` does not notice a register-facts change today. One-line fix, before anything else.

### 1. HouseSpec, the one record (`src/canalRecall/houseSpec/`)
- **Vocabulary is not new**: the design fields are `HouseDesign` (= `CanalHouseIntent` minus identity) from `blockFace/intent.ts`; `houseIntents(face)` already turns every face house into a validated intent, and recipes and block faces speak it. The spec wraps it: `{ schemaVersion: 1, pandId, design: DeepPartial<HouseDesign>, provenance: Record<fieldPath, {source, confidence, ref, at}>, schemaLimits?: string[], route?: 'generic'|'recipe' }` (`spec.ts`). Provenance machinery comes from `facade/evidence.ts` (`Measured`, `SOURCE_STRENGTH`, `resolveField`), with `'vision-judge'` added between `pdok-ortho` and `bag` and `'author'` = `'reviewed'`. `resolve.ts` merges partial specs field by field, strongest source wins. Nothing invented: a missing field stays undefined.
- **Adapters, not rewrites** (`adapters.ts`): block face (`houseIntents`, provenance `streetlevel-measured` with the strip as ref, `rhythm.schemaLimits` + face `limitations` → `schemaLimits`), recipe intent (`canal-house` kinds only: 35 of 207 on main, 166 are `large`), `houseRecord` (gable word map trap→step, hals→neck, klok→bell, tuit→spout, lijst→cornice…), register (`registerPatch` inputs, source `monument-text`, ref = register number; absorbs a1's `registerRecipe.ts`), Jev (bays, pui, source `vision-judge`, confidence ≈ 0.6). `toRecipe.ts` spec → `CanalHouseIntent` only for the `recipe` route (complete = `validateIntent` passes). The 222 house intents and 901 face intents stay where they are and become the first spec sources.
- **Extract**: `public/data/extracts/amsterdam/house-specs/14/x/y.json.gz` (resolved compact fields), loaded by a `houseSpecEnricher` in `gameTileEnricher.ts` like roof facts (`p.houseSpec`), listed in `pipeline.ts tileInputs(t)` so a spec edit rebuilds the 6–9 cells that list that tile, not the city.
- **First consumer, the generic streamed path**: `decorate.ts withHouseSpec` in `gameFeatureDecorator` right after the register step (spec outranks register). It writes properties the chain already honours (`monumentGable`, `constructionYear`, `registerFinish`) plus one new `specRecipe`: an `ArchitecturalRecipe` subset (`crownShape`, `period`, `wallHex`, new `bays`) that fills the existing `MeshBuilding.recipe` slot (`streetAppearance.ts`, today filled only from street-appearance profiles); `meshBuildingFor` sets `recipe ??= p.specRecipe`, `frontageLayoutScale` (`streetFacadeRendering.ts:95`) derives the bay width from `bays` when present. A plain BAG box grows its register gable and measured bays with no GLB. This is what fixes the Nieuwmarkt row. Cell attributes already encode nested objects, so `specRecipe` bakes into world-v1 cells. Second consumer: `blockFace/compile.ts` reads the spec for pands without a hand intent. GLB paths unchanged.
- Flag `?houseSpecs=0` byte-identical, same pattern as the register flag.

### 2. Preview in Node (`npm run house:preview -- <pandId|spec.json> [--watch] [--photo]`)
- No dev server, no Playwright. Files: `scripts/house-preview/preview.ts`, `scripts/house-preview/nodeDom.ts` (stubs), `src/canalRecall/houseSpec/softRaster.ts`. Pipeline: `pipeline.ts loadTile` with `gameChain()` and a spec override → neighbours from `BuildingContextIndex` → `shellStreets` for street fronts → `buildFeatureChunk` in `walls` then `extras` mode → the same footprint-wall choice as `pand-reference/rectify.ts rectifyWall` (so photo and render share one axis at 50 px/m) → `softRaster` extends `renderElevation`'s triangle loop with uv interpolation, `fract` wrap, atlas sampling by vertex layer and the shader's tint/accent/shade mix (`threeBuildingsBrowser.ts:189`; atlas rows are stored flipped), near tier only, 2× supersampling; 3/4 view = same rasteriser with a perspective matrix. `useBrowserMath` imported first; chunk frame is ORIGIN-local metres.
- Stubs: `document.createElement('canvas')` → napi `createCanvas` (must accept `getContext('2d', {willReadFrequently})`), `document.baseURI` → `pathToFileURL('public/canal-drive/')`, `Image` → shim whose `src` setter loads the file via napi `loadImage`; the preview asserts the `Bricks057` image actually loaded (the painter silently falls back otherwise). Atlas paint is seconds: cache `artifacts/house-preview/atlas-<look>-<painter-hash>.bin`; watch mode keeps tile, context, streets and atlas warm → under 0.5 s a render, under 3 s cold-with-cache.
- Scoring: `likeness.ts` cannot score the generic path (it takes a per-triangle `MaterialSoup`), so run `buildingRecipe/measureFacade.ts` on both the render and the photo and apply the `likenessVerdict` thresholds. Writes `artifacts/house-preview/<pand>/{front,threeq,compare}.png`; `compare` is render beside `staging/pand-reference/<pand>/front.jpg` or the block-face strip crop. Recipe-route specs use the existing GLB compile + `renderElevation` + the same `measureFacade` comparison. `render.ts` (SwiftShader) stays as the fallback.

### 3. Stage and publish in batches
- `house:stage <pand>` (`scripts/house-specs/stage.ts`): validate the spec, write `artifacts/house-specs/staging/<pand>.json`, run the preview as the receipt (compare PNG path + verdict recorded). Lanes stop here. Nothing in `public/` changes.
- `house:publish` (`scripts/house-specs/publish.ts`, integrator, nightly or on demand): merge staged specs into the tiled extract with a per-pand diff → `world:compile --changed --shell` (touched cells only; the shell-hash guard stays) → if any spec has the recipe route: install, `build-covers`, publish covers → goldens with `--allow=<pand ids>` (`test:fit-golden`, `large-mesh-hashes`, `roof-golden`, `test:block-kit-installed`: changes inside the list re-record, any change outside fails; for the generic route the per-cell world compare is the guard, cells outside the batch's tiles must decode identically) → one `check:canal` per batch → one commit and one HISTORY/What's New entry per batch. Staged specs and compare sheets are archived to `map-recall2-source-data`.
- `pipeline.ts`/`compile.ts`: remove `COVERS` from `GLOBAL_INPUTS`; hash each tile's covers slice (hidden ids for that tile's building ids, from a `tile-ids.json` written on a full run, or `build-covers.ts` emitting `covers-by-tile`) into `tileHash`; the `--against` coversKey special case becomes a per-cell comparison of hidden lists.
- Stale installs: a spec that edits an installed recipe house makes its GLB stale; publish reinstalls it or writes `held-installs.json` with reason `staged spec <date>`, then `check:stale-installs --strict` runs. GLB installs continue to use `install*.ts` and ride in the same nightly run.

### 4. Describe at scale (crops → facts → spec)
- `house:crops --buurt <code>`: for every pand with a street-facing BAG wall in the ride-priority buurten (centre + inner ring, memory `buurt-priority-by-ride`), run the existing `pand-reference/select.ts` + `rectify.ts` (fallback `block-face/intake.ts planStrip` for rows), flag with the existing `foliageFraction`/`washedOutFraction`/`missingFraction`, archive to `map-recall2-source-data/pand-crops/<pand>/`, one request per 500 ms, resumable. Pilot: one canal-belt buurt (~2,000 pands) before the city.
- `house:describe <pand|--buurt>`: writers in order of trust: register facts (date, type, gable, finish, elements) → pixel measurement (`buildingRecipe/measure.ts` palette, glazing, storeys from the crop) → Jev typed judge (`bays` ±1, `pui`, `gable` only when confident, `finish`) → 3DBAG/BAG (heights, year). Each writer fills only its `FIELD_SOURCES` fields and never overwrites a higher-trust value. Output is a spec; the lane reads the compare sheet and corrects by hand only where likeness is WARN/FAIL.

### 5. The kit-gap queue
- `scripts/house-specs/kit-gaps.ts` aggregates `schemaLimits` from resolved specs (keyed by the component before the colon), block-face `limitations` via the adapter, and `rhythm.schemaLimits`, into `artifacts/kit-gaps/queue.json` as `{gap, weightedCount, pands[], examples[]}`; a pand weighs 3 inside `RIDE_PRIORITY_GEBIEDEN` (moved from `scripts/register-facts/build-monument-facts.ts:15` to `src/canalRecall/ridePriority.ts`), else 1. `docs/handoffs/kit-gaps.md` becomes a generated view plus prose notes.
- Horizon rule (new, named in the doc; the only rule today is the weekly kit session "takes the top two"): a gap goes to a kit lane when its weighted count reaches 50 or one landmark needs it; below that the house ships with the nearest option and the limit recorded. House lanes stop extending the kit themselves; the weekly kit session takes the top two of the queue.

### 6. Documentation (user, 2026-11-10: "make sure the pipeline you build is well documented in the right places, CLAUDE.md where appropriate, for future claude runs to pick up")
- `docs/house-line.md` is the one canonical pipeline doc: the five stations, every command with its flags, where specs/crops/staging/archives live, the trust order of writers, the horizon rule, and a worked example (one pand from crop to publish). `docs/START-HERE-buildings.md` and `docs/buildings-pipeline.md` get a pointer at the top and lose the superseded steps.
- `CLAUDE.md` gets a short "House line" section under architecture notes: house lanes write specs and stage, never install or recompile; the five commands; the doc to read; the horizon rule; the batch publish is the integrator's. Nothing longer than ten lines, with the detail in `docs/house-line.md`.
- Every command prints `--help` from the same text the doc uses (one `HELP` constant per script, the doc test `test:house-line-docs` checks the doc lists every `house:*` npm script and every flag).
- Every lane's hand-back includes its doc diff; a lane that ships a command without its doc section is not done. `HISTORY.md` records why the line exists (this plan's Context) when H1 lands.
